# Единая архитектура: jobsignal + autoapply

## Зачем объединение

Два сервиса делали одно и то же. `jobsignal` собирает вакансии, оценивает
релевантность и пишет сопроводительные письма. `autoapply` делал ровно то же
самое заново — и дополнительно умел отправлять отклик на hh.ru через браузер.

Отправка — единственное, чего у `jobsignal` не было и что нельзя сделать иначе:
API hh.ru для соискателей закрыт, кнопку «Откликнуться» можно нажать только
живым браузером с авторизованной сессией.

Поэтому `autoapply` перестаёт быть отдельным сервисом и становится исполнителем
внутри `jobsignal`.

## Конвейер

```
источники                 обработка                      отправка
─────────                 ─────────                      ────────
Telegram-каналы  ─┐
                  ├─→ parse → dedup → match → compose ─→ status=drafted
hh.ru (поиск)    ─┘         (скоринг)  (письмо)              │
                                                             ├─ contact_type=tg   → notify_bot
                                                             └─ contact_type=hh   → autoapply
                                                                                      │
                                                              Application.sent_at, status=applied
```

Ни парсинга, ни скоринга, ни вызовов Claude в `autoapply` не остаётся —
только браузер и кнопка. Это убирает и повторный расход API на те же вакансии.

## Модель данных

Схема `jobsignal` (SQLite + SQLAlchemy, `jobsignal/db.py`) уже покрывает всё
нужное — заводить новые таблицы под отклики не требуется:

| Таблица | Роль |
|---|---|
| `Channel`, `RawPost` | источник: Telegram-каналы и сырые посты |
| `Vacancy` | вакансия; статусы `new → matched → drafted → applied → replied` |
| `Vacancy.draft_text` | сгенерированное сопроводительное письмо |
| `Vacancy.contact_type` | канал отклика: `tg` / `hh` / `form` / `unknown` |
| `MatchScore` | оценка релевантности с обоснованием, по профилям |
| `Application` | факт отклика: `sent_at`, `replied_at`, `notes` |
| `ChannelCandidate` | найденные каналы, ожидающие проверки |

Точка стыковки: `autoapply` забирает `Vacancy` со `status=drafted` и
`contact_type=hh`, отправляет отклик, проставляет `Application.sent_at`
и переводит вакансию в `applied`.

## Состояние кода

Каталог `jobsignal/` — полный код с рабочего сервера (3057 строк Python,
39 файлов), выгруженный через `git archive` из отобранного вручную набора.
В выгрузку намеренно не попали: `config/.env` с токенами, база `data/`,
файл сессии Telegram `jobsignal_session.session` и посторонние личные файлы,
которые оказались в том же каталоге.

Конвейер (`orchestrator.py`) гоняет по расписанию только сбор и оценку:

```
CollectorAgent → ParserAgent → DeduplicatorAgent → MatcherAgent
```

`ComposerAgent` и `OutreachAgent` в периодический цикл не входят — они
запускаются из дашборда по кнопке. Режим задаётся `outreach_mode`:
`SEMI_AUTO` (по умолчанию) или `FULL_AUTO`.

Это удачно ложится на встройку `autoapply`: он становится ещё одним
исполнителем на том же шаге, что и `OutreachAgent`, но для `contact_type=hh`.

## Где что развёрнуто сейчас

| | Путь на европейском сервере |
|---|---|
| jobsignal | `/opt/jobsignal_local`, venv `.venv`, база `data/jobsignal.db` |

| дашборд | порт 5000, наружу закрыт ufw, доступ через SSH-туннель |

Запуск дашборда: `tmux new -s dash`, внутри
`cd /opt/jobsignal_local && .venv/bin/python run.py serve`.
Туннель с рабочей машины: `ssh -N -L 8090:127.0.0.1:5000 root@130.17.20.195`,
далее `http://localhost:8090`.

Ключ SSH настроен в одну сторону: российский сервер ходит на европейский,
не наоборот. Все переносы файлов запускаются с российского.

## Известные дефекты

- `autoapply`: флаг `--limit` не ограничивает прогон — объявлен бюджет в 3 вакансии,
  обработано 40. Вакансии с ошибкой не списываются с бюджета. В боевом режиме
  это угроза дневному лимиту откликов.
- `autoapply`: селекторы hh.ru устаревают. `mainmenu_applicantProfile` и
  `mainmenu_myResumes` уже исчезли, заменены на `mainmenu_profileAndResumes` и
  `mainmenu_applicantProfilePage`. Проверку залогиненности стоит делать по
  редиректу, а не по вёрстке меню.
- Сессия hh.ru (`state.json`) живёт ограниченное время и обновляется только
  вручную с машины с дисплеем. Нужен механизм напоминания об истечении.
