# Единая архитектура: jobsignal + autoapply

## Зачем объединение

Два сервиса делали одно и то же. `jobsignal` собирает вакансии, оценивает
релевантность и пишет сопроводительные письма. `autoapply` делал ровно то же
самое заново — и дополнительно умел отправлять отклик на hh.ru через браузер.

Отправка — единственное, чего у `jobsignal` не было и что нельзя сделать иначе:
API hh.ru для соискателей закрыт, кнопку «Откликнуться» можно нажать только
живым браузером с авторизованной сессией.

Поэтому `autoapply` перестаёт быть отдельным сервисом и становится исполнителем
внутри `jobsignal`.

## Конвейер

```
источники                 обработка                      отправка
─────────                 ─────────                      ────────
Telegram-каналы  ─┐
                  ├─→ parse → dedup → match → compose ─→ status=drafted
hh.ru (поиск)    ─┘         (скоринг)  (письмо)              │
                                                             ├─ contact_type=tg   → notify_bot
                                                             └─ contact_type=hh   → autoapply
                                                                                      │
                                                              Application.sent_at, status=applied
```

Ни парсинга, ни скоринга, ни вызовов Claude в `autoapply` не остаётся —
только браузер и кнопка. Это убирает и повторный расход API на те же вакансии.

## Модель данных

Схема `jobsignal` (SQLite + SQLAlchemy, `jobsignal/db.py`) уже покрывает всё
нужное — заводить новые таблицы под отклики не требуется:

| Таблица | Роль |
|---|---|
| `Channel`, `RawPost` | источник: Telegram-каналы и сырые посты |
| `Vacancy` | вакансия; статусы `new → matched → drafted → applied → replied` |
| `Vacancy.draft_text` | сгенерированное сопроводительное письмо |
| `Vacancy.contact_type` | канал отклика: `tg` / `hh` / `form` / `unknown` |
| `MatchScore` | оценка релевантности с обоснованием, по профилям |
| `Application` | факт отклика: `sent_at`, `replied_at`, `notes` |
| `ChannelCandidate` | найденные каналы, ожидающие проверки |

Точка стыковки: `autoapply` забирает `Vacancy` со `status=drafted` и
`contact_type=hh`, отправляет отклик, проставляет `Application.sent_at`
и переводит вакансию в `applied`.

## Состояние кода

Каталог `jobsignal/` — полный код с рабочего сервера (3057 строк Python,
39 файлов), выгруженный через `git archive` из отобранного вручную набора.
В выгрузку намеренно не попали: `config/.env` с токенами, база `data/`,
файл сессии Telegram `jobsignal_session.session` и посторонние личные файлы,
которые оказались в том же каталоге.

Конвейер (`orchestrator.py`) гоняет по расписанию только сбор и оценку:

```
CollectorAgent → ParserAgent → DeduplicatorAgent → MatcherAgent
```

`ComposerAgent` и `OutreachAgent` в периодический цикл не входят — они
запускаются из дашборда по кнопке. Режим задаётся `outreach_mode`:
`SEMI_AUTO` (по умолчанию) или `FULL_AUTO`.

Это удачно ложится на встройку `autoapply`: он становится ещё одним
исполнителем на том же шаге, что и `OutreachAgent`, но для `contact_type=hh`.

### Про «79 откликов и 0 ответов»

Эта пара цифр вводит в заблуждение, и на неё не надо опираться. Разбор базы
показал, что **65 из 79 записей — нажатия кнопки «я откликнулся»** в дашборде,
которой отклик отмечается вручную. Система по ним ничего не отправляла:
`dashboard/app.py:318` пишет в `applications` пустой `message_text` и канал
`tg`, из-за чего ручные отметки неотличимы от настоящих отправок.

Автоматика за всё время отправила **7 писем** (Telegram, два дня в июне).
Ноль ответов на семь отправок — рядовая статистика, объяснять её качеством
текста или обрывом писем нечем.

Единственный отклик на hh.ru тоже не был отправлен агентом: он ушёл при
навигации на `/applicant/vacancy_response`, письмо приложено вручную. Из
четырёх боевых попыток на hh: две `needs_manual`, одна `no_letter_field`,
одна вот эта. Агент не отправил через hh.ru ещё ни одного письма.

Проверка писем в `draft_text`: 49 штук, ни одного обрезанного, длины 686–1729
при медиане 1039. Гипотеза про обрыв по лимиту токенов не подтвердилась —
письма на hh.ru генерируются через `notify_bot._cover_text`, где лимит 2000,
а не через `composer.py` с его 400 (тот пишет `applications.message_text`
для Telegram).

Настоящие потери лежат **до** письма: 65 × archived, 11 × no_respond_button,
11 × not_allowed, 10 × forbidden. Это история журнала попыток, а не состояние
очереди: `drops_vacancy` уводит archived/gone/not_allowed в `skipped`, а
`FORBIDDEN_GIVE_UP` убирает вакансию после трёх 403, так что все они уже
закрыты. Очередь сейчас — 5 вакансий с нормальными черновиками.

Одна утечка того же класса была настоящей и починена: `needs_manual` (анкета
работодателя) не считался терминальным, хотя повтором не лечится — вакансия
оставалась `drafted` и занимала слот в каждом прогоне. Вакансия #1096 съела
так 7 попыток, #5426 — пять. При квоте 3 отклика в час это часы простоя.

## hh.ru с европейского сервера

Два следствия того, что сервер стоит в Европе, — оба неочевидные и оба
ломали отклики.

**Модалка «You are applying from another country».** hh.ru показывает её на
**каждом** отклике, а не изредка. Пока селектор кнопки подтверждения был
неверным, модалка не закрывалась, перекрывала форму, поле письма не
находилось — и отклик не мог пройти в принципе, независимо от вакансии.
Правильный `data-qa` — `relocation-warning-confirm`.

**Интерфейс отдаётся на английском.** Поэтому любые проверки по тексту в
агенте будут ломаться. Всё должно держаться на `data-qa`, и это правило
стоит соблюдать во всех будущих правках.

**API поиска вакансий закрыт для этого адреса — перепроверять не нужно.**
`api.hh.ru/vacancies` отдаёт `403 {"errors":[{"type":"forbidden"}]}`, причём
в заголовках `server: ddos-guard`: отбивает антибот-прослойка, а не
приложение hh. Авторизация тут ни при чём — этот API открытый и токена не
требует, дело именно в репутации адреса. Проверено семью способами
(10.09.2026), все семь дают 403:

| способ | результат |
|---|---|
| `curl` без заголовков | 403 |
| `curl` с UA `JobSignal/1.0` | 403 |
| `curl` с браузерным UA | 403 |
| `requests` с 37 куками сессии из `state.json` | 403 |
| Playwright, `APIRequestContext.get` | 403 |
| Playwright, тот же запрос после визита на hh.ru (куки ddos-guard получены) | 403 |
| Playwright, переход страницей на URL API | 403 |

Закрыт весь раздел вакансий, включая `api.hh.ru/vacancies/<id>`. Соседние
эндпоинты на том же хосте (`/areas`, `/dictionaries`) отдают 200, так что
хост целиком не блокирован.

**Данные берём из состояния страницы, а не из вёрстки.** Сам hh.ru
открывается обычным `requests` и даже без сессии, а страницы несут готовый
JSON в `<template id="HH-Lux-InitialState">`:

- выдача `https://hh.ru/search/vacancy` → `vacancySearchResult.vacancies`:
  50 карточек на страницу, рядом `totalResults` и `paging`. Поля
  `vacancyId`, `name`, `company`, `compensation`, `area`, `workExperience`,
  `workFormats`, `creationTime`. Описания в выдаче нет;
- страница `https://hh.ru/vacancy/<id>` → `vacancyView.description` (HTML,
  чистится от тегов) и `keySkills`.

Поэтому `hh_collector` не разбирает разметку: перестановка карточек и смена
классов ему безразличны. Уязвимых мест ровно два — имя блока состояния и
путь к ключам.

**Молчаливый ноль запрещён.** Старый коллектор возвращал «добавлено 0» с
конца июня, конвейер шёл дальше как ни в чём не бывало, и мёртвый сбор не
замечали два с половиной месяца. Теперь пропавший блок состояния,
изменившийся путь к ключам, отказ всех запросов подряд или ноль карточек по
всем поискам поднимают `HHStructureChanged`. Пустая выдача по одному запросу
при этом остаётся законным результатом. `run.py pipeline` дорабатывает
остальной конвейер (телеграм-часть от hh не зависит), но пишет ошибку в лог
и выходит с кодом 1.

## Сбор с hh.ru не работает с конца июня

Боевой прогон 10.09 это подтвердил: `hh_collector` получил **HTTP 403 на всех
восьми запросах**, добавлено 0 вакансий. Самая свежая вакансия с
`contact_type='hh'` в базе — конца июня.

То есть очередь на отклик не «стареет» — она не пополняется. Всё, что в ней
есть, попало туда перепечатками из Telegram. Это и объясняет, почему половина
вакансий оказывалась архивной к моменту отклика.

Отклик при этом работает: он идёт через Playwright с авторизованной сессией, а
сборщик — обычными HTTP-запросами. hh.ru режет зарубежные дата-центровые
адреса без авторизации, а браузерный трафик с сессией пропускает.

Прежде чем писать браузерный сбор, надо проверить открытый JSON API поиска:

```
https://api.hh.ru/vacancies?text=product+manager&area=1
```

Авторизация для поиска не нужна — у соискателей закрыт только отклик, ради
которого и держится браузер. Если API отвечает с этого сервера, это лучший
вариант: структурированный JSON вместо парсинга вёрстки, которая будет
ломаться, и никакого Playwright для сбора.

## Возраст вакансии — открытый вопрос

Из 87 вакансий hh.ru, прошедших порог, **50 оказались архивными** к моменту
попытки отклика. Код с ними справляется — уводит в `skipped` и очередь не
засоряется, — но это упущенные возможности: вакансии закрылись, пока лежали
в очереди.

Отсюда следует, что наращивать скорость отправки бессмысленно: узкое место не
в квоте 3 отклика в час, а в том, что до вакансии не успевают дойти. Работать
надо над сокращением пути от появления вакансии до отклика.

Что для этого нужно измерить: время от `created_at` до попытки отклика,
отдельно для успешных и для тех, что оказались архивными. Если архивные
систематически старше — станет виден порог, после которого откликаться
бессмысленно, и место, где теряется время: частота сбора, задержка матчинга
или накопление очереди на отправку.

| **клон репозитория** | `/root/visa` — сюда коммитим |

| `/root/autoapply`, `/opt/jobparser` | старое, не используется — логика перенесена в `agents/hh_apply.py` |

**Репозиторий и деплой — разные каталоги с разной структурой.** Соответствие:

```
/opt/jobsignal_local/jobsignal/llm.py  ↔  /root/visa/jobsignal/jobsignal/llm.py
/opt/jobsignal_local/run.py            ↔  /root/visa/jobsignal/run.py
```

То есть весь деплой соответствует подкаталогу `jobsignal/` в репозитории.
`git init` в деплое делать не надо: структура не совпадёт, а `config/.env`,
`data/` и резюме там лежат рядом с кодом.

Правки делаются в деплое, потом копируются в клон и коммитятся оттуда.

Запуск дашборда: `tmux new -s dash`, внутри
`cd /opt/jobsignal_local && .venv/bin/python run.py serve`.
Туннель с рабочей машины: `ssh -N -L 8090:127.0.0.1:5000 root@130.17.20.195`,
далее `http://localhost:8090`.

Ключ SSH настроен в одну сторону: российский сервер ходит на европейский,
не наоборот. Все переносы файлов запускаются с российского.

## Известные дефекты

- `autoapply`: флаг `--limit` не ограничивает прогон — объявлен бюджет в 3 вакансии,
  обработано 40. Вакансии с ошибкой не списываются с бюджета. В боевом режиме
  это угроза дневному лимиту откликов.
- `autoapply`: селекторы hh.ru устаревают. `mainmenu_applicantProfile` и
  `mainmenu_myResumes` уже исчезли, заменены на `mainmenu_profileAndResumes` и
  `mainmenu_applicantProfilePage`. Проверку залогиненности стоит делать по
  редиректу, а не по вёрстке меню.
- Сессия hh.ru (`state.json`) живёт ограниченное время и обновляется только
  вручную с машины с дисплеем. Нужен механизм напоминания об истечении.
- `jobsignal`: письма пишутся двумя независимыми путями. `agents/composer.py`
  берёт текст из `config/cv_*.md` и пишет короткое сообщение в TG;
  `agents/notify_bot.py::_cover_text` берёт текст из таблицы `resumes` и пишет
  сопроводительное — этим путём идут дашборд и бот, то есть боевой он. Правка
  промпта в одном пути на другой не влияет: правило про даты работы, добавленное
  в `composer.BASE_SYSTEM`, боевую генерацию не затрагивает. Захардкоженный
  список компаний из `_cover_text` убран — он перебивал резюме и любое
  обновление мест работы до модели не доходило.
- `jobsignal`: таблица `resumes` — снимок текста PDF, а не сам PDF. Обновляется
  только загрузкой через `/resumes` или ручным `parse_and_save()`. Подмена
  `config/master_cv.pdf` на диске снимок не трогает, и письма продолжают
  писаться по старому: так и вышло — в базе лежал текст от 01.07.2026, где
  ФИНАМ значился «настоящее время», хотя резюме давно переписали. Все три
  профиля теперь привязаны в `profiles.yaml` к общему `config/master_cv.pdf`;
  извлечение текста требует `pypdf`, которого в venv не было.
