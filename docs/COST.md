# Снижение расходов на API

## Откуда берутся цифры

Оценки ниже — расчётные, по коду и текущим ценам. Прежде чем что-то менять,
снимите факт: `response.usage` возвращает `input_tokens`,
`cache_creation_input_tokens`, `cache_read_input_tokens` и `output_tokens`.
Сейчас эти поля нигде не логируются — это первое, что стоит добавить, иначе
экономию не с чем будет сравнить.

Цены (Claude API, за 1M токенов):

| Модель | Вход | Выход |
|---|---:|---:|
| `claude-sonnet-5` — матчинг и письма | $2 | $10 |
| `claude-haiku-4-5` — парсинг постов | $1 | $5 |

Чтение из кэша стоит ~0.1× от цены входа, запись в кэш — 1.25× (TTL 5 минут).
Окупается со второго запроса.

## Профиль расхода

Основной потребитель — `MatcherAgent`. Один вызов на вакансию, но в системный
промпт кладутся все три резюме: `CV_CAP = 4000` символов × 3 профиля ≈ 12 000
символов. На кириллице это порядка 4000–5000 токенов, и они одинаковы для всех
вакансий прогона.

Грубая оценка одной вакансии сейчас: ~4500 токенов резюме + ~800 описание +
~200 выход ≈ **$0.013**. На 6344 вакансиях — порядка $80, и это без учёта
неограниченного описания (см. ниже).

## Что делать, по убыванию отдачи

### 1. Кэширование системного промпта — бесплатно, без потери качества

Сейчас в `llm.py` система уходит строкой:

```python
resp = _get_client().messages.create(
    model=model, max_tokens=max_tokens, system=system, ...
)
```

Нужно передавать её блоком с точкой кэширования:

```python
def _anthropic_text(system, user, model, max_tokens, cache_system=False):
    system_param = system
    if cache_system:
        system_param = [{
            "type": "text",
            "text": system,
            "cache_control": {"type": "ephemeral"},
        }]
    resp = _get_client().messages.create(
        model=model, max_tokens=max_tokens, system=system_param,
        messages=[{"role": "user", "content": user}],
    )
    log.info("usage: in=%d cache_w=%d cache_r=%d out=%d",
             resp.usage.input_tokens,
             resp.usage.cache_creation_input_tokens,
             resp.usage.cache_read_input_tokens,
             resp.usage.output_tokens)
    return "".join(b.text for b in resp.content if getattr(b, "type", None) == "text")
```

Включать для матчера и композера — у них система стабильна внутри прогона.

Условия, при которых это сработает:

- Минимальный кэшируемый префикс у `claude-sonnet-5` — **1024 токена**.
  Системный промпт матчера (~4500) проходит с запасом. У `claude-haiku-4-5`
  минимум **4096**, и короткий системный промпт парсера, скорее всего, не
  дотянет — там кэширование не поможет, не тратьте на него время.
- TTL 5 минут, отсчёт от начала запроса. Матчер идёт вакансия за вакансией по
  несколько секунд, так что кэш держится сам. Отдельный TTL на час не нужен.
- Порядок сборки промпта — `tools` → `system` → `messages`. Резюме должны быть
  в `system` и не меняться внутри прогона; текст вакансии идёт в `messages`,
  после точки кэширования.

Ожидаемо: вход по резюме падает с ~4500 до ~450 токенов на вакансию,
стоимость вакансии — примерно с $0.013 до **$0.0045**, то есть около **−64%**.

Проверка, что заработало: `cache_read_input_tokens` должен быть больше нуля
начиная со второй вакансии прогона. Если ноль — где-то в системный промпт
просочилось что-то меняющееся, и кэш ломается молча, без ошибки.

### 2. Обрезать описание вакансии — бесплатно, чинит утечку

`matcher.py`, функция `_vacancy_text`:

```python
f"Описание: {v.description or '—'}"
```

Ограничения нет. Резюме обрезаются по `CV_CAP`, парсер режет текст по 3000
символов, а здесь описание уходит целиком. Одна многословная вакансия
обходится как десяток обычных, и заметить это по логам сейчас невозможно.

Поставить потолок — 2500–3000 символов. Требования и обязанности почти всегда
в начале, на качество оценки это не влияет.

### 3. Дешёвый фильтр до матчера — бесплатно, крупнейший выигрыш по объёму

Из 6344 вакансий **5556 отсеяны по порогу — 88%**. Почти весь бюджет матчера
уходит на подтверждение «не подходит».

Часть этого решается без модели вообще: стоп-слова в заголовке (`junior`,
`стажёр`, `Haskell`, `выпрямительные системы`), несовпадение уровня,
нерелевантный домен. Каждая отсеянная так вакансия — это сэкономленный вызов
Sonnet целиком, а не его удешевление.

Если хочется точнее — двухступенчатая схема: `claude-haiku-4-5` даёт грубое
«да/нет» по заголовку и первым строкам описания, и только прошедшие идут в
Sonnet на полноценную оценку по трём профилям. Haiku вдвое дешевле на входе и
работает по куда более короткому промпту.

Осторожно с порогом отсева: цель — убрать заведомо чужие вакансии, а не
подменить матчер. Прежде чем включать, прогоните фильтр на уже оценённых
вакансиях и посмотрите, не выбрасывает ли он то, что матчер оценил выше порога.

### 4. Batch API — −50%, ничего не меняя в промптах

Матчинг и парсинг не интерактивны: это фоновый конвейер, никто не ждёт ответа
на экране. Batch API даёт **половину цены** за асинхронную обработку.

Подходит для `MatcherAgent` и `ParserAgent`. Не подходит для композера, если
письмо генерируется по кнопке из дашборда и пользователь ждёт результат.

Кэширование в батчах работает, но прогрев запросом с `max_tokens: 0` внутри
батча запрещён — если понадобится прогрев, делайте его обычным запросом.

### 5. Выбор модели — последнее, что стоит трогать

Сейчас `ANTHROPIC_MODEL=claude-sonnet-5`. Это разумный выбор для матчинга и
писем, и понижать его до Haiku ради экономии не стоит: качество оценки прямо
определяет, куда уйдут отклики, а плохо подобранная вакансия стоит дороже
сэкономленных центов.

Правильный порядок — сначала бесплатные рычаги выше. Модель трогать только
если после них расход всё ещё велик, и тогда — измеряя качество на уже
оценённых вакансиях, а не на глаз.

## Срочно: парсер сломается на Anthropic

`config.py` объявляет `parser_model: claude-haiku-4-5`, но это поле **нигде не
используется**. Парсер и бот уведомлений передают пустую строку вместо модели:

```python
raw = complete_text(SYSTEM, prompt, "", 400)          # agents/parser.py:196
return complete_text(system_prompt, user, "", 350)     # agents/notify_bot.py:182
```

На GigaChat это работало: `_gigachat_chat` игнорирует параметр `model` и берёт
модель из конфига. У Anthropic `messages.create(model="")` вернёт ошибку.
Матчер и композер уцелели — они передают модель явно.

Починка: пробросить `cfg.settings.parser_model` в парсер и notify_bot. Заодно
это включает замысел «дешёвая модель для разбора», который в конфиге есть, но
не подключён.

## Дублирующие сценарии

### Письма генерируются двумя разными путями

`composer.generate_draft` и `notify_bot._cover_text` делают одно и то же —
пишут сопроводительное — но это независимый код с разными промптами. Свести в
один путь: один промпт, одна точка правки, один расход.

### Парсер работает до дедупликации

Порядок конвейера — `collector → parser → dedup → matcher`. Одна вакансия
висит в нескольких каналах, и каждый репост уходит в модель на разбор; дедуп
выбрасывает лишние уже после, когда за них заплачено.

Дедуп при этом бесплатный — нормализованные ключи, никаких эмбеддингов.
Значит грубый дедуп сырых постов по хешу нормализованного текста можно делать
**до** парсера. Каждый отсеянный репост — сэкономленный вызов целиком, а не
его удешевление.

Точный дедуп по роли и компании остаётся на своём месте: эти поля появляются
только после разбора.

## Что уже сделано правильно

Не трогать, чтобы не сломать:

- **Разбор PDF-резюме кэшируется в базе.** `parse_and_save` пишет текст,
  `get_resume_text` читает; повторно PDF не парсится.
- **Матчер идемпотентен.** Берёт только `NEW` и `SKIPPED` без оценок,
  повторный прогон не переоценивает уже посчитанное.
- **Один вызов на вакансию, а не по одному на профиль.** Три профиля
  оцениваются в одном запросе.
- **hh_collector не ходит в модель** — забирает структурированные поля со
  страницы напрямую.

## Разделение моделей по объёму

Экономить нужно там, где объём, а не там, где качество решает исход. Вакансий
тысячи, писем — единицы.

| Шаг | Объём | Модель |
|---|---|---|
| Парсинг постов | тысячи | `claude-haiku-4-5` |
| Отсев заведомо чужих | тысячи | без модели, стоп-слова |
| Грубый отбор | сотни | `claude-haiku-4-5` |
| Точная оценка по трём профилям | десятки–сотни | `claude-sonnet-5` |
| Генерация письма | единицы | `claude-sonnet-5` |

Кэши привязаны к модели, поэтому двухступенчатый отбор ломает переиспользование
кэша между ступенями: у Haiku и Sonnet будут разные записи. При малом объёме
второй ступени это не страшно — но если после включения кэширования и фильтра
объём Sonnet упадёт до десятков вакансий за прогон, двухступенчатость может
перестать окупаться. Мерить после первых трёх правок, а не до.

## Стоп-слова из уже оплаченных данных

Самая дешёвая оптимизация: разметка уже есть. 5556 отсеянных и 614 прошедших
порог — это выборка, за которую уже заплачено.

Один раз, обычным SQL без единого вызова модели, вытащить из заголовков слова,
которые часто встречаются у отсеянных и почти не встречаются у прошедших:

```sql
-- частота слова среди отсеянных против прошедших
-- (набросок; реальный запрос требует разбиения role на слова)
select lower(role), count(*) from vacancies
where status = 'skipped' group by 1 order by 2 desc limit 100;
```

Полученный список даёт фильтр, который дальше работает вечно и бесплатно.

**Проверка обязательна:** прогнать фильтр по 614 прошедшим порог и убедиться,
что он не выбрасывает ни одной. Слово, встречающееся хотя бы у одной
подошедшей вакансии, в стоп-лист не идёт.

## Сводно

| Мера | Эффект | Риск для качества |
|---|---|---|
| Пробросить `parser_model` | чинит поломку | нет |
| Логирование `usage` | видимость | нет |
| Кэширование системного промпта | −64% на вакансию | нет |
| Потолок на описание вакансии | чинит утечку | нет |
| Дедуп сырых постов до парсера | минус все репосты | нет |
| Свести два пути генерации писем | меньше кода, не токенов | нет |
| Стоп-слова из своей же разметки | −50…60% объёма | есть, нужна проверка |
| Двухступенчатый отбор | Haiku вместо Sonnet на объёме | есть, нужна проверка |
| Batch API | −50% | нет, только задержка |
| Смена основной модели | разное | есть, трогать последней |

Меры без риска вместе дают порядка **−65…70%**. Со стоп-словами и батчами —
примерно **−85%** от текущего.

## Что сделать в первую очередь

Порядок важен: без первых двух пунктов остальное либо не заработает, либо
эффект будет не видно.

1. Пробросить `parser_model` в парсер и notify_bot — иначе они просто упадут.
2. Логировать `usage` во всех вызовах.
3. Включить кэширование в `_anthropic_text` для матчера и композера.
4. Поставить потолок на `v.description` в `_vacancy_text`.
5. Дедупить сырые посты по хешу текста до парсера.
6. Прогнать матчер на 20 вакансиях и сверить `cache_read_input_tokens` с нулём
   до правки.

Стоп-слова, двухступенчатый отбор и батчи — следующим заходом: они требуют
проверки на качество, а перечисленное выше не требует.
